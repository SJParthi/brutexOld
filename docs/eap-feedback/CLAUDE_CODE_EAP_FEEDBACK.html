Tier 2 · The 5 topics at a glance

Beta verdict, organized by your 5 topics

In short: the Projects beta shines for long-lived, multi-agent work — its memory and autonomy genuinely carry the weight. The rough edges are in the beta itself: observability (no progress on long jobs, no up-front cost estimate) and a real reliability lesson we hit — a single beta agent will confidently self-certify a wrong answer unless a second agent checks it.

TopicVerdictWhat the beta does wellWhere the beta needs work
1 · Use-case fit 👍 Strong Project memory makes rules, scope & ceilings inherit with zero restating. Key Project state lives in prose, not queryable fields.
2 · Reliability ⚖️ Mixed Sessions finish autonomously — a PR was opened, gated & merged end-to-end. A lone beta agent self-certified a fake benchmark; only a second beta agent caught it.
3 · Memory 👍 Strong The beta's memory carried rules, scope & rate ceilings across sessions; it turned a rule into a check that caught a hallucinated citation. The beta's memory isn't queryable — facts are buried in long prose.
4 · Proactivity ⚖️ Mixed Parallel fan-out, adversarial review & background jobs all run on their own. No progress heartbeat on long jobs; no up-front cost estimate.
5 · Session-mgmt UX ⚖️ Mixed Completed-work triage is good — structured worker summaries. No per-session base-state header before you steer a session.

👍 Strong works well   ⚖️ Mixed good with real friction   ⚠️ Needs work material gap

Tier 3 · Key findings

The findings most worth acting on

The high-impact, actionable beta issues we hit firsthand — each describes a Claude Code Projects beta behaviour (BruteX is only the workload we observed it on, never the subject), with a severity and a suggested fix. Severity legend: S2 high S3 medium.

SevBeta finding (behaviour we observed)Suggested fix
S2A lone beta agent self-certified a fake 3.57× benchmark (a GIL-releasing time.sleep standing in for a GIL-bound disk write) and declared the gate "proven"; only the beta's own adversarial reviewer re-measured the real ~1.17× and blocked the merge. Single-agent self-certification isn't safe; multi-agent review is.Independently re-measure any agent-produced perf claim against the real primitive — never trust a self-graded speedup.
S2The beta spawned a worktree on a disjoint git base — no common ancestor with the live tip, no local ref at the real tip (branch / main / origin/main all on the stale commit), so recent files were absent. The agent correctly stopped, but only after a ~250s wasted run with zero usable output.Seed spawned envs from live HEAD; hard-fail if git merge-base with the live tip is empty; expose the live tip as a ref/env-var in every spawned env.
S2Long background jobs give no progress heartbeat — we watched a ~31-min run give zero intermediate signal until done, indistinguishable from a hung one in any list view.Periodic heartbeats (step / elapsed / progress) to the coordinator, reflected in the session list as a liveness indicator.
S2The beta's autonomously-opened PR tripped the repo's own gates (PR-body markers / Definition-of-Ready / citation scan) because it didn't first read the mandatory PR template.On autonomous PR creation, read the repo's PR template + gate config and pre-populate the body to satisfy them.
S3Project memory isn't queryable — authoritative facts ("active branch", current ledger #) sit deep inside long prose, and we saw a stale-base session get actively misled by it.Promote {active_branch, current_ledger_no, open_prs, scope_lock} to structured fields read first.
S3Scheduled routines were not reachable from the beta's session toolset, so recurring / proactive work couldn't be set up from the agent. (A big fan-out we ran, ~1.5M tokens, also had no up-front cost estimate — only a live meter after launch.)Expose routine / scheduled-trigger setup to the agent toolset; add a pre-flight cost estimate for large fan-outs.

The strongest beta wins we observed firsthand — Claude Code Projects beta behaviours worth keeping.
