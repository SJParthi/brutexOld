Tier 2 · A little more

One card per topic

The headline plus the single biggest win and the single biggest friction for each. Skim these; the full itemized findings are in Tier 3 below.

1 · Use-case fit — when to reach for a Project

BruteX is the textbook "reach for a Project" case: long-lived, ledger-driven work that must survive across sessions.

  • The 12 project rules, scope lock, and rate ceilings inherit automatically — no restating per session.
  • Authoritative state (active branch, current ledger #) is buried in a ~1,230-line prose file, not exposed as queryable fields.

2 · Reliability — do sessions finish autonomously?

Yes — with strong self-correction, but the sharpest lesson of the week sits here.

  • A PR was opened, gated, and merged start-to-finish by the session; a second risky PR was correctly held as a NO-GO. The system both finishes good work and refuses bad work.
  • The key finding: a lone agent produced a fake 3.57× benchmark (it modeled a disk write as a GIL-releasing time.sleep) and declared the gate "proven" — only the independent adversarial reviewer re-measured the real ~1.17× and blocked it.
  • A worktree was seeded on a disjoint git history; the agent correctly stopped, but only after a ~250s wasted run.

3 · Memory — does it let me skip restating?

Yes — one of the program's clearest wins.

  • Rules, scope, rate ceilings, and ledger discipline all carried forward with zero restating.
  • Memory turned "every claim must trace to a real ledger entry" into a mechanical check that caught a hallucinated citation.
  • Facts aren't queryable — the most-needed "active branch" sits deep inside a long paragraph; a stale-base agent can be actively misled.

4 · Proactivity — does it work & set up routines on its own?

Yes, materially — the friction is observability and cost, not initiative.

  • Parallel worker fan-out, an adversarial reviewer, a workspace-health verifier, and background long-jobs all ran proactively. Live token spend was visible in the background panel.
  • Long background jobs give no progress heartbeat — a 31-min run looks identical to a hung one.
  • A big multi-agent fan-out (~1.5M tokens) had no up-front cost estimate — only a live meter after launch.

5 · Session-management UX — which session needs attention?

Completed-work triage is good; the gaps are at the top of the funnel.

  • Structured worker→coordinator summaries (file:line, hashes, pass counts) make finished work easy to triage.
  • No per-session base-state header (which env / branch / merge-base) before you steer it.
  • An autonomously-opened PR tripped the repo's own gates because it didn't pre-read the required PR-template markers.
