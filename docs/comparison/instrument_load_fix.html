📚 The 10-second story

Imagine a library with 162,256 books. One book has a blank spine — no title.

❌ Before: the librarian saw that one untitled book and locked the entire library. Nobody could read anything. Doors shut. Error sign on the front.

✅ After: the librarian sets that one book aside with a sticky note ("can't shelve this — no title"), and opens the library. All 162,255 other books are ready to read.

❌ Before — the bug

One malformed vendor row poisoned everything

  • You click “Load instruments”
  • App hits the broken row → crashes the whole load
  • Screen shows HTTP 502 error
  • App starts with 0 instruments — useless
  • It keeps retrying and failing on every restart

✅ After — this fix

One bad row can never sink the ship

  • You click “Load instruments”
  • App skips the bad row, keeps the good ones
  • Screen shows success (HTTP 200)
  • App loads 111,699 instruments — ready to work
  • Bad row is logged with a note so you can see it

🛡️ The one principle behind it

Harden against bad DATA — never mask bad CODE.
Bad data from the vendor (a blank field, a stale number) → quietly skipped and noted, so you’re never blocked. But a broken file format or a real bug in our code → still stops loudly, because those are things you genuinely need to know about. We don’t sweep real problems under the rug.
