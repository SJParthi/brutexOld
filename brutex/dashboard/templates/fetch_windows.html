ℹ️ How to read a row — attempts · EMPTY-retries (↻) · EMPTY x/3 · the 3× retry
attempts = number of pulls, not network fetches — within each pull an empty window is automatically re-fetched up to 3× before it is recorded (the in-pull empty-retry), so attempts 1 already means up to 3 fetches happened this pull.
fetches = the in-pull EMPTY-retry depth of the last pull — i.e. how many times the empty/transient re-fetch loop re-issued THIS window before recording it. 1 = a clean first-try; ↻ 3 (amber) = the window came back empty and was re-fetched 3× this pull; — = a planned window not yet fetched.
This is NOT the total vendor calls. It does NOT include the deeper timeout / 429 retry ladder a FAILED window also burns: each of these fetches internally retries up to 6× on a timeout / rate-limit (the in-call ladder), and the whole window can be re-tried across multiple transient passes and pull rounds — so a FAILED row reading fetches 1 may have actually made many more vendor calls than the number shown here (only the EMPTY-retry depth is persisted per window, not the in-call ladder count).
EMPTY x/3 = the vendor returned a clean, empty response on x of 3 separate pulls; the window is re-checked every pull and only settles as a durable no-data gap at 3/3 (reverted 10→3 per DEC-REALDATA-ONLY-NO-1M-TO-1D-001, MIGRATION.md #852 — the 1m→1d resample that the 10-round persistence existed to feed is removed, so a recent-stock daily empty is honestly terminal; a 429 / timeout preserves the streak, it is not evidence of data).
A genuine vendor gap (e.g. Groww serves no SENSEX 1-day before ~2022, no FINNIFTY before ~2025) stays EMPTY ↻ 3 however many times it is retried — there is simply no data to fetch, and BruteX never fabricates one (Golden Rule #1).
